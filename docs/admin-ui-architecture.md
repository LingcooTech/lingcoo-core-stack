# fd-core-stack Admin UI 架构基线

> 本文保留早期后台架构演进记录。后续管理后台迁移与页面优化按 [Stack 管理后台 Ant Design 迁移与 Edu 对齐方案](admin-ant-design-migration-plan.md) 执行；该方案制定于 2026 年 10 月 10 日，尚不代表迁移已经实施。

## 1. 目标

管理后台要从“功能堆叠页”升级为“资源驱动的控制台”。

Laravel Nova 式后台的核心不在某个颜色或卡片样式，而在下面几件事：

- 有稳定的 shell：侧边栏、顶部条、页面标题、资源上下文都不乱跳
- 有统一的资源索引层：列表优先，详情次之，表单是操作而不是页面主角
- 有统一的状态语言：badge、pill、empty、detail、danger action 都一致
- 有一致的扩展路径：新增资源页时复用现成骨架，而不是复制粘贴一整页 HTML

## 2. 当前差距

相对 Nova 一类成熟后台，当前项目原始 UI 的主要差距集中在结构层，不只是视觉层。

### 2.1 资源心智不够强

原来的后台更像一个“大型设置页”：

- 登录、支付、应用、授权、运营、观测全部堆在同一模板里
- 页面主视觉偏介绍式，不是资源式
- 资源索引、资源详情、资源动作之间没有明确层次

Nova 的做法相反：

- 先定义资源，再定义索引、过滤、详情和动作
- 文案是辅助，资源列表才是主角

### 2.2 信息密度明显偏低

原先的后台大量使用卡片块和说明文字，适合营销页或设置页，不适合运营后台：

- 列表资源被渲染成卡片流，扫描效率低
- 同屏信息量不足
- 状态、金额、时间、关联对象没有压进统一的行结构里

### 2.3 缺少列表原语

Nova 的核心是资源表格，而不是“很多卡片”。

原先缺失的原语包括：

- 可复用表格容器
- 统一表头、行高、hover、边框和滚动
- 统一 cell stack 结构
- 统一状态 pill
- 列表和详情的主次关系

### 2.4 UI 配置层缺位

导航、标题、路径、模块说明都散落在大模板里：

- 页面配置不是单一来源
- 后续新增模块时容易复制旧结构
- 视觉与信息架构耦合过深

## 3. 这次建立的基础层

### 3.1 资源定义层

新增文件：

- `src/modules/admin/ui-foundation.ts`

这个文件现在承接：

- admin section 定义
- 导航分组
- route 映射
- 资源标题、说明和上下文卡片

这一步的意义是让“资源配置”从页面模板中独立出来，后续新增后台域时先加配置，再接页面内容。

### 3.2 后台壳层

当前后台 shell 已收敛到一套固定结构：

- 左侧导航
- 顶部工具条
- 页面级 breadcrumb + title + actions
- 左侧上下文 rail
- 右侧资源内容区

这套结构比原先更接近 Nova 的工作方式，后续新增资源无需重新设计壳层。

### 3.3 列表基础组件

当前已落地的列表原语：

- `table-card`
- `table-scroll`
- `data-table`
- `cell-stack`
- `pill`
- `cell-actions`

已经切到表格展示的资源：

- 应用列表
- 订单列表
- 安装实例
- 授权明细
- 业务事件
- 支付回调

这一步是与 Nova 差距收缩最大的改动，因为它直接决定后台是否具备“资源索引页”的形态。

### 3.4 统一状态语言

目前已经统一的状态表达包括：

- `ok`
- `warn`
- `danger`
- `neutral`

这些 tone 同时用于：

- 状态 pill
- provider / type 标签
- 空态和危险动作的视觉分层

### 3.5 Route-Scoped 数据加载

这次继续推进后，后台页不再默认把所有资源都加载一遍。

现在每个 section 都在 `src/modules/admin/ui-foundation.ts` 里声明自己的 `pageDataScopes`，页面运行时按 scope 决定加载什么数据：

- `payments` 只加载支付配置
- `apps` 只加载应用索引和产品目录
- `licenses` 只加载套餐与 entitlement 列表
- `operations` 只加载订单、安装与关联详情
- `observability` 只加载事件流与支付回调
- `dashboard` 才加载全量汇总数据

这一步的意义不是省几次请求，而是让“路由 = 资源页边界”这件事真正成立。后续新增后台域时，不需要再担心一个页面把别的域的数据和状态一并拖进来。

### 3.6 命令式搜索入口

Nova 风格后台的一个重要特征，是“全局找入口”不依赖记菜单。

当前后台已经补上命令式搜索基础层：

- 顶部搜索触发器
- `/` 与 `Cmd/Ctrl + K` 快捷键
- 按 section schema 生成的 command index
- 资源页、文档页和状态页的统一跳转入口

命令搜索本身并不复杂，但它把后台导航从“只能点侧边栏”推进到了“可以命令式调度资源页”。这对后续资源越来越多时的可扩展性非常重要。

## 4. 页面组合规则

后续后台页建议统一遵守下面的组合顺序：

1. Page Header
2. Context Rail
3. Resource Sections
4. Table First
5. Detail Second
6. Form / Action Last

含义：

- 先让用户看见当前资源是什么
- 再给筛选、状态和上下文
- 再展示资源列表
- 需要时才打开详情或危险动作

不要再回到“长文案 + 多卡片 + 列表附属化”的结构。

## 5. 仍然存在的差距

这次改造把 UI 从“早期后台页”推进到了“有后台架构基础的资源控制台”，但还没到 Nova 的完整程度。

下一阶段仍需补齐：

- 真正的分页而不是固定 limit
- 列排序
- 批量选择与 bulk action
- 每个资源的独立详情页或抽屉
- 过滤器栏而不是只在局部写 select
- 更完整的图标体系
- 空态、加载态、错误态的统一骨架
- 审计日志与操作时间线

## 6. 判断标准

后续新增后台页面时，可以用下面三条自检：

- 这是不是一个资源页，而不是说明页
- 列表是不是主视图，而不是被卡片挤到边缘
- 新页面是否复用了现有 shell、pill、table、cell-stack 和 section 配置

如果三条都满足，后台就会继续朝 Nova 方向稳定收敛。
