# 应用与托管分开计费、组合结算

状态：已确认方向，尚未实现组合订单与托管履约。自然月/年日期边界已修正。独立托管服务期限（试用/人工授予）已上线验证，尚未接入付费履约。本文不代表正式商品已开售。

## 用户已确认的产品方向

应用与托管分别计费，可合并订单。平台先提供月付、年付及客户主动续费。应用价格、托管价格分别配置，年付是否折扣由商品配置决定，不自动假定折扣比例；不引入自动扣款。

## 订单与履约模型

- 首期仅做同一应用的软件与托管组合，避免提前建设跨应用购物车。
- 一个结算单、一次渠道支付、多条不可变价格明细；每条明细保存商品、类型、数量、金额、币种和周期快照，金额由服务端计算。
- 软件明细发放软件权益；托管明细产生可激活的服务资格。独立存储履约来源，不借软件 entitlement 的有效期表达托管期限。
- 老单品订单保持兼容；托管续费不得重新购买软件或增加可部署数量。
- 付款回调、主动对账、重复回调必须在事务中实现单次履约。支付失败、退款和取消不伪造付款成功。

## 服务周期

1. 预付托管购买后先等待分配/部署。首次公网交付 ready 才确定周期锚点，失败重试不消耗周期。
2. 月、年以自然月和年计算，月底向目标月末截断，连续续费从原始锚点算第 N 个周期，防止日期漂移。
3. 到期前续费延长现有到期日，不能从付款日重新起算导致已付天数丢失。
4. 首次交付、重新部署、恢复、迁移分别建模；重新部署不得重置付费期限。
5. 到期宽限期、停服后的数据保留期为可配置政策，且应在购买前向客户展示。实现日期状态不等同于授权自动删库；回收仍按独立退出流程执行。
6. 已有试点实例保留可审计的测试/人工授权来源，不把“当前在运行”转换成“已付费”或“永久免费”。

## 退款和售后

- 组合支付必须支持明细级退款记录及累计退款上限，不能只支持整单退款后同时撤销两种服务。
- 未激活托管的取消与运行中托管的终止分别处理；按实际商业政策计算可退金额，不由镜像卸载动作决定退款。
- 软件明细退款只处理其软件权益；托管明细退款只处理对应服务记录。任何退款都不直接删除客户业务卷。
- 每次变更保留订单、服务、操作者、原因及版本，客服可从部署台账追踪。

## 发布门槛

- 组合订单金额、币种、价格快照；重复回调与并发续费；跨用户/跨应用资格使用；首次交付计时；月底和闰年；单项退款及重复退款均有隔离测试。
- 正式价格和支付渠道确认后，再安排真实付款、退款与渠道核对。
- 客户端、后台、账单和工单展示相同的明细、期限与状态，不仅提供后台 API。

参考：Stripe 的周期锚点文档 https://docs.stripe.com/billing/subscriptions/billing-cycle 。这里借鉴周期计算与状态分离，不代表要切换现有微信/支付宝渠道。

## 第二阶段分步交付

### 2A：独立服务期限（本次实现）

- 每个托管部署拥有至多一个独立服务期记录，未登记的旧实例保持未登记，不反推付款事实。自有服务器不能登记托管服务。
- 仅管理员拥有 `hosting.terms.manage`，客服/运营沿用部署读取权限；客户只能查询本人部署，不能查看内部变更原因。
- 首期支持 trial/manual，登记必须明确月/年、周期数、宽限天数、停服后保留天数和原因。不提供 paid 人工选项，也不生成支付记录。
- 未交付时等待；公网 DNS/HTTPS 及所属实例验证完成后，在交付事务中自动激活。已经交付的旧实例从管理员显式登记的时间起算，不倒推或补扣历史费用。
- 到期前延长沿用原始锚点；到期（包括宽限期）后重新授予服务，从本次就绪时建立新锚点；尚未就绪时等待交付。每次变更的前后快照和原因留存。
- 请求标识 + 版本校验 + 部署行锁保证重试不叠加、并发变更不覆盖；交付重复回报不重置期限。
- 到期、宽限为实时计算的合同状态，不触发容器停止、数据删除或未配置的外部通知；保留天数暂为合同政策记录，退出流程接入后才执行。
- 沿用现有后台蓝灰色语义样式、字体和卡片组件，以折叠面板嵌入部署详情、托管实例和客户部署卡片；管理员表单与只读信息分区，手机端单列。

### 2B：付费履约（后续实现，尚未交付）

继续完成独立托管商品、组合订单明细、支付后授予资格、资格与部署绑定、客户主动续费及分项退款。2A 的人工延长不等于商业续费；在 2B 验收前不能宣称完整托管收费已上线。

### 2B 前置：支付渠道退款协议

适配器区分原始支付总额和本次退款金额，同一退款请求复用固定退款编号。未传分项信息时兼容原整单退款编号；分项退款必须显式传编号与金额，金额按整数分验证。确认退款成功前需核对原订单、退款编号和金额；微信处理中响应同样核对，异常不推进本地已退款状态。

支付宝查询 `code=10000` 只表示查询成功，只有 `refund_status=REFUND_SUCCESS` 才能认定退款成功；尚未确认时保留处理中状态。整单退款业务层另行校验全额，避免将未来的单项退款误当作全单退款并撤销软件权益。本改造不直接开放部分退款 HTTP 接口，也未执行真实退款。

依据：

- https://aipay.alipay.com/docs/vibe-pay/ai-web-app-payment-qianyi/api-list/alipay-trade-fastpay-refund-query.html
- https://aipay.alipay.com/docs/vibe-pay/ai-web-app-payment-qianyi/api-list/alipay-trade-refund.html
- https://pay.wechatpay.cn/doc/v3/merchant/4012791884
- https://pay.wechatpay.cn/doc/v3/merchant/4012810597

退款响应真实性：支付宝退款与退款查询明确开启现有 SDK 的 `validateSign`；微信 V3 退款与查询使用现有 `WECHAT_PAY_PLATFORM_CERT` / `_PATH` 配置验证签名，并检查五分钟时间窗口。微信退款前必须提供平台验签证书/公钥，不能仅配置商户私钥；未配置时在发出退款请求前失败。此项不替代后续真实渠道小额验收，当前测试使用临时生成的测试密钥和模拟响应。

### 2B 套餐目录实施边界

托管套餐使用独立 `hosting_offers` 表（billing 所有），不可更换所属应用或稳定编码，支持草稿/上架/下架；金额为人民币整数分，月付与年付分别建套餐，不推算折扣。零价仅供草稿/下架保存。每次修改保留版本和前后审计；版本冲突需刷新，创建重试复用 UUID。

后台入口：托管运维 → 托管套餐，仅管理员可用。界面继承现有后台字体、蓝灰语义色、卡片和手机单列布局。到期宽限与停服后保留天数必须显式填写，未创建正式售卖价格。套餐配置不改变运行实例或服务期。

目录上线不等于开放托管付费。后续订单必须保存套餐版本、金额和政策快照，付款履约只能依据订单快照；禁止用可编辑目录反推历史订单。组合订单、资格绑定和分项退款未验收前，不提供客户托管付款入口。

### 2B 购买快照基础

订单新增 `items` JSONB 明细；新软件订单在创建时保存应用/商品名称、商品标识、计费周期、数量、单价、金额和币种，服务端验证明细合计。快照与订单在同一 INSERT 中写入，数据库触发器拒绝后续改写快照或已含快照订单的金额/币种/应用/软件套餐关联。退款和支付状态更新仍被允许。

旧订单保留空明细，明确提示缺少历史购买快照，不根据当前商品资料回填。客户订单、后台订单详情和结算页展示同一份快照；公共页面使用 textContent 渲染商品标题。重新发起结算时，仅在当前报价与原快照一致时复用待支付会话，避免套餐改价后错误复用旧报价。

此批只完成购买金额与展示快照，不冻结软件功能授权定义，也尚未接通托管组合付款。后续需扩展托管明细的版本及服务政策快照，接入资格发放、绑定、续费和分项退款后，再开放客户组合购买。
