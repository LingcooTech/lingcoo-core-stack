# 跨节点恢复：隔离验证先行

## 要求与验收

1. 当运维指定独立保存的快照校验摘要、源部署/操作及目标节点时，恢复器必须先验证全部文件、归属、可信适配器和镜像；不接受“最新备份”这种不稳定引用。
2. 当归档损坏、路径越界、容量不足或目标卷不属于当前恢复操作时，拒绝恢复，不修改既有客户资源。
3. 恢复只创建独立恢复卷，不启动业务 API、Worker、定时任务，不写 DNS、平台分配或生产网关；节点离线不能作为已隔离的证明。
4. 重复执行同一冻结计划必须复用已验证结果；中断后的半成品必须明确报错，不能覆盖数据或假报成功。
5. 从异机 Restic 的固定快照取回数据，在另一台服务器验证 PostgreSQL 数据和文件，记录耗时及清理结果。

## 设计

`hosting-node-recover.py` 为运维 CLI，使用现有节点私有配置和 v2 可信适配器。输入计划固定恢复 ID、部署 ID、源冷快照操作 ID、目标节点 ID、SHA256SUMS 摘要、容量上限。恢复目录独立于 agent workspace，Docker 卷以恢复 ID 命名并带独立归属标签。全程持有恢复目录文件锁。

冷快照必须是 `lingcoo-cold-volumes-v1`；普通应用自定义逻辑备份不能伪装成冷卷快照。先校验摘要及严格文件清单，再校验配置归属、适配器文件摘要、固定镜像、tar 路径/链接/内容/展开容量。逐卷还原后重新归档并逐文件比较内容、权限、UID/GID及链接目标。失败保留恢复日志及卷供核对，只能通过归属核验后的清理命令删除。

Restic 下载只接受完整快照 ID、精确备份路径和部署标签，按已验证清单逐文件读取，禁止自动执行备份中的脚本。不会输出数据库连接串或原始备份日志。

## 后续切流准入（本批不开放生产按钮）

必须另行实现源节点可靠隔离、平台维护状态和双节点容量预留、目标实例接管、业务就绪验证、默认及自定义域名切换、DNS 延迟窗口、故障回退与旧节点保留账本。目标开始接受写入之后，禁止自动切回旧数据。当前 82 节点保持仅监控；隔离测试不赋予其生产调度资格。
