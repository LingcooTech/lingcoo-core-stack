管理后台重构方案

这份文档只解决一件事：把后台按“开发接入、商品建模、运营中心、系统设置”重新整理清楚。 重点是把应用接入、商品售卖、授权定义、运营管理彻底拆开，避免继续把产品页做成一个什么都塞的配置页。

应用负责接入 产品负责售卖 价格负责收费 授权分模板与结果两层

左侧菜单

仪表盘

开发接入
  应用列表

商品建模
  产品
  价格方案
  授权档位

运营中心
  交易管理
  用户管理
  授权管理
  实例管理
  事件管理
  日志管理

系统设置
  支付配置
左侧菜单只保留一级业务入口。复杂内容都放到“列表页 -> 详情页 -> Tab”里，不再继续堆二级、三级导航。

最重要的边界

开发接入

回答“是谁在接中台”。只管应用身份、密钥、回调、部署、交付、允许卖哪些产品。

商品建模

回答“卖什么、怎么卖、买完属于什么档位”。只管产品、价格方案、授权档位。

运营中心

回答“系统跑起来后怎么查、怎么管、怎么排障”。只管订单、支付、用户、授权结果、实例、事件、日志。

不再允许在产品页里同时配置应用密钥、回调、部署信息，也不再让运营后台手工定义一堆 feature code 作为真实权限源。

全局呈现方式

对象类型 推荐呈现 说明
资源集合 表格列表页 产品、应用、用户、订单、授权、实例、事件、日志都应先用表格承载。
复杂资源 详情页 + Tab 应用详情、产品详情、用户详情适合拆分成多个区块，不再用超长表单。
轻量编辑 抽屉 价格方案、授权档位这类结构稳定的对象适合列表页右侧抽屉新增和编辑。
危险操作 二次确认弹窗 停用、撤销、删除、重置密钥等操作必须和普通编辑分开。
详情查看 抽屉或独立详情页 订单、事件、日志可以优先用抽屉，用户、应用、产品适合独立详情页。

目标路由清单

这里给的是重构后的推荐路由。原则是：列表页有独立路由，复杂详情页有独立路由，详情内部用 Tab，不再把每个小模块都做成左侧菜单。

模块 路由 用途
仪表盘 /admin 系统概览、异常提醒、最近动态。
应用列表 /admin/applications 查看所有接入应用。
应用详情 /admin/applications/:applicationCode 查看和配置单个应用的接入信息。
产品列表 /admin/products 查看所有商品。
新建产品 /admin/products/new 创建新商品。
产品详情 /admin/products/:productCode 查看和编辑单个产品。
价格方案 /admin/pricing 统一管理所有价格方案。
授权档位 /admin/authorization-templates 统一管理授权档位模板。
交易管理 /admin/transactions 订单与支付的统一入口，内部再分订单/支付 Tab。
用户管理 /admin/users 查看和管理用户。
授权管理 /admin/authorizations 查看和处理已经发出去的授权结果。
实例管理 /admin/instances 查看安装实例和部署实例。
事件管理 /admin/events 查看业务事件流。
日志管理 /admin/logs 查看系统日志和错误日志。
支付配置 /admin/settings/payments 配置微信支付和支付宝。
当前代码里大量功能还堆在 /admin/products 及其详情页里。目标是把应用接入、商品建模、交易运营拆成独立资源页。

模块一：仪表盘

作用：看全局，不承担深度配置。

区块 呈现方式 内容
核心指标 指标卡 成交额、订单数、有效授权数、活跃用户数、活跃实例数。
异常提醒 告警列表 支付失败、授权失败、回调异常、实例异常。
最近动态 时间流 最近订单、最近授权、最近事件。

模块二：开发接入

作用：管理应用如何接入中台。这里是技术身份管理，不是商品售卖管理。

页面：应用列表

呈现方式：表格列表页。

主要列 操作
应用名称、应用标识、类型、状态、已绑定产品数、最近活跃、更新时间 查看详情、启用/停用、签发密钥

页面：应用详情

呈现方式：独立详情页，使用 Tab 分区。

Tab 内容
基本信息 应用名、应用标识、应用类型、状态、说明。
应用密钥 当前密钥、创建时间、最后使用时间、失效时间、重新生成。
API 接入信息 appCode、鉴权方式、调用地址、签名要求、示例请求。
回调配置 支付回调地址、业务回调地址、白名单域名、回调状态。
交付/部署配置 交付方式、部署模板、环境变量模板、交付说明。
可售产品 绑定该应用允许售卖的产品。
应用详情回答的是“这个软件怎么接中台、怎么调用中台、怎么交付”，不回答“这个软件卖多少钱”。 
应用详情页结构

页头
-> 应用名称 / 应用标识 / 状态 / 类型
-> 快捷操作：启停、签发密钥、查看调用文档

概要区
-> 已绑定产品数
-> 最近活跃时间
-> 当前交付方式
-> 当前密钥状态

Tab 1 基本信息
Tab 2 应用密钥
Tab 3 API 接入信息
Tab 4 回调配置
Tab 5 交付/部署配置
Tab 6 可售产品

模块三：商品建模

作用：把软件商业化。这里只定义产品、价格方案、授权档位，不再混入应用接入配置。

应用接入中台
-> 给应用绑定可售产品
-> 产品定义对外卖什么
-> 价格方案定义怎么收费
-> 授权档位定义买完属于什么级别
-> 用户购买价格方案
-> 系统发放对应授权结果

页面：产品列表

呈现方式：表格列表页。

主要列 操作
产品名、产品标识、分类、状态、价格方案数、授权档位数、已绑定应用数、更新时间 查看详情、上架/下架

页面：产品详情

呈现方式：独立详情页，使用 Tab 分区。

Tab 内容
基本信息 名称、标识、图标、封面、分类、简介、详细介绍。
销售展示 标题、副标题、卖点、购买说明、默认展示文案。
价格方案 当前产品下所有价格方案的嵌入表格。
授权档位 当前产品下所有授权档位的嵌入表格。
售卖应用 哪些应用可以售卖这个产品。
产品详情里不再出现应用密钥、回调配置、部署配置，也不再出现“功能项勾选矩阵”。 
产品详情页结构

页头
-> 产品名称 / 产品标识 / 状态 / 分类
-> 快捷操作：上架、下架、新增价格方案

概要区
-> 价格方案数
-> 授权档位数
-> 已绑定应用数
-> 最近成交或更新时间

Tab 1 基本信息
-> 名称、标识、图标、封面、分类、简介、详情介绍

Tab 2 销售展示
-> 副标题、卖点、购买说明、前台展示文案

Tab 3 价格方案
-> 内嵌表格，展示当前产品下所有价格方案

Tab 4 授权档位
-> 内嵌表格，展示当前产品下所有授权档位

Tab 5 售卖应用
-> 哪些应用可以卖这个产品

页面：价格方案

呈现方式：表格列表页 + 右侧抽屉编辑。

主要列 编辑字段
方案名、所属产品、收费方式、计费周期、金额、币种、状态、对应授权档位 所属产品、方案名、内部标识、收费方式、计费周期、金额、币种、状态、对应授权档位

这里的重点是“怎么卖”，不是“给哪些底层功能打勾”。

页面：授权档位

呈现方式：表格列表页 + 右侧抽屉编辑。

主要列 编辑字段
档位名、所属产品、档位标识、说明、状态、关联价格方案数 所属产品、档位名、档位标识、说明、状态
这里定义的是商业授权级别，例如免费版、专业版、企业版。应用内部自己决定每个档位真正开放哪些功能。

模块四：运营中心

作用：业务发生后，用来查看、处理、纠错、排障。

页面：交易管理

呈现方式：一个页面，分“订单”和“支付”两个 Tab。

Tab 主要列
订单 订单号、用户、产品、价格方案、金额、支付方式、状态、下单时间、支付时间。
支付 支付单号、关联订单、支付渠道、支付状态、回调状态、错误信息、更新时间。

页面：用户管理

呈现方式：表格列表页 + 右侧详情抽屉。

主要列 详情内容
邮箱、昵称、状态、注册时间、最近登录、订单数、授权数 基本资料、订单、授权、实例、事件。

页面：授权管理

呈现方式：表格列表页 + 详情抽屉。

主要列 操作
用户、产品、授权档位、来源、状态、生效时间、到期时间、关联订单 补发、撤销、延期、试用发放
这里管理的是已经发出去的授权结果，不是商品建模里定义的授权档位模板。

页面：实例管理

呈现方式：一个页面，分“安装实例”和“部署实例”两个 Tab。

Tab 主要列
安装实例 实例 ID、用户、应用、产品、设备信息、版本、状态、最后活跃。
部署实例 实例 ID、用户、应用、产品、服务器、域名、状态、部署时间、最后心跳。

页面：事件管理

呈现方式：时间流表格。

主要列 筛选条件
事件名、应用、产品、用户、实例、来源、时间 按应用、产品、用户、订单、实例、时间范围筛选。

页面：日志管理

呈现方式：日志表格或分栏日志查看器。

分类 主要列
API 日志、任务日志、错误日志、回调日志 时间、级别、模块、请求 ID、摘要，点击后查看完整日志正文。

模块五：系统设置

作用：放系统级配置，不和业务对象混在一起。

页面：支付配置

呈现方式：Provider 卡片 + 配置表单。

Provider 配置项
微信支付 AppId、商户号、证书、私钥、回调地址、启用状态。
支付宝 AppId、私钥、公钥、回调地址、启用状态。

当前页面怎么拆

下面这一段是最关键的迁移方案。目标不是推倒重来，而是把现在塞在产品中心里的内容分流到正确页面。

当前集中在产品中心的内容 迁移后应该去哪里 处理原则
产品基本信息 产品详情 / 基本信息 保留，继续作为产品详情的核心部分。
产品卖点、亮点、展示文案 产品详情 / 销售展示 保留，但明确它只影响前台展示，不影响真实授权。
基础 Plan 价格方案 整体迁到独立的价格方案页，不再放在产品页长表单里维护。
能力项 / feature code 不再作为后台自由编辑项 如果以后确实需要细粒度能力，改成应用侧声明、中台侧映射，不再由运营后台现场发明。
授权方案 授权档位 改造成“授权档位模板”，只定义免费版、专业版、企业版这类级别。
销售方案 / offer 产品详情 / 销售展示 或价格方案的展示属性 保留展示属性，但不能再把它当成真实授权逻辑来源。
交付声明、部署配置、环境变量 应用详情 / 交付与部署配置 整体迁出产品页，因为它属于应用接入与交付，不属于商品定义。
应用关联 应用详情 / 可售产品，产品详情 / 售卖应用 两边都可以看，但主维护入口建议在应用详情。 
推荐迁移顺序

第 1 步
先把应用列表和应用详情重新立起来

第 2 步
把产品中心里的交付/部署相关内容迁到应用详情

第 3 步
把产品中心里的基础 Plan 拆到价格方案页

第 4 步
把“授权方案”改造成“授权档位模板”

第 5 步
把旧的 feature 勾选逻辑逐步下线

第 6 步
最后把产品详情页收敛成“基本信息 + 销售展示 + 价格方案 + 授权档位 + 售卖应用”

最终落地原则

  • 应用页只配接入，不配价格。
  • 产品页只配商品，不配密钥和部署。
  • 价格方案页只配收费，不配底层功能勾选。
  • 授权档位页只定义“买完属于什么级别”。
  • 授权管理页只看已经发出去的授权结果。
  • 实例管理页只看软件实际装在哪、部署在哪。
  • 商品建模和运营中心必须彻底分开。
