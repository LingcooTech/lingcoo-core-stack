# Stack 应用开发与交付模板

这份目录应合并进应用自己的开发仓库；无需创建额外的公开 delivery 仓库。仓库可公开或私有，ACR 只存储镜像。生成器拒绝覆盖已有目录，先生成到新目录再审查合并。

## 第一次使用

1. 阅读并修改 `stack/app.yaml`：应用 code 应保持稳定；填写介绍、许可、素材、功能权益与真实入口。模板默认免费、`UNLICENSED`，请按实际许可选择，不自动推定开源。
2. 在应用目录运行 `npm run stack:validate`。`scripts/stack-toolkit.cjs` 自包含平台的定义校验器，只需 Node 22，无需安装 Stack 或访问平台。
3. Compose 模板带一个可运行的 Node HTTP 样本：`npm test`、`npm start`，访问 `http://localhost:8080` 与 `/health`。用自己的业务实现替换样本，再调整 Dockerfile、Compose、健康检查和测试。
4. 在有 Docker 的开发机执行 `docker build -t my-app:test .` 和 `npm run test:image -- my-app:test`。该脚本仅适用于模板的单服务入口；数据库、Worker 等多服务应用应扩展为完整组合验收。
5. 在 Stack 从仓库导入并创建应用草稿，生成该应用的 CI 发布凭证，保存为仓库 Secret `STACK_PUBLISH_TOKEN`；变量 `STACK_API_URL` 填平台 HTTPS 地址。
6. Compose 应用还需配置 Secret `ACR_REGISTRY`、`ACR_USERNAME`、`ACR_PASSWORD`。镜像仓库来自 app.yaml；多组件应分别构建并登记全部摘要，不能只登记 web。
7. 工作流文件合并到默认分支后，使用 Stack 触发构建或手动 workflow_dispatch，传入完整 40 位提交和版本。CI 固定源码、测试、推送 ACR 并登记草稿。PR 验证不使用发布凭证。
8. 完成平台实际交付验收和商业配置后再发布、上架。CI 通过不会自动销售、修改价格或升级已有客户实例。

源码校验器更新：用新版 Stack 生成到另一目录，核对差异后替换工具；`stack/toolchain.json` 记录工具 SHA-256。CI 中固定的工具提供可复现检查，平台接收时仍使用当前服务端规则再次验证。

## 分工与唯一来源

| 内容                                     | 唯一负责方         | 同步规则                                               |
| ---------------------------------------- | ------------------ | ------------------------------------------------------ |
| 应用标识、默认介绍、素材、许可、功能声明 | 应用仓库           | 首次导入填充草稿；后续同步候选定义，商业信息由后台确认 |
| 镜像、Compose、配置声明、生命周期操作    | 应用仓库           | 随固定源码提交构建为不可变交付版本                     |
| 软件售价、套餐权益、上架状态、托管价格   | Stack              | 不从仓库自动覆盖                                       |
| 客户参数、真实密钥、节点、域名、证书     | Stack / 自部署客户 | 不进入源码或镜像；每个实例独立保存                     |
| 编译、应用测试、镜像推送                 | 应用 CI            | 使用镜像推送凭证；运行时只用拉取凭证                   |
| 购买、授权、部署资格、履约、托管运维     | Stack              | 消费已发布版本，不实时读取浮动分支部署                 |

`features` 只声明能力名称和标识，不代表销售配额，也不会自动实现应用内鉴权。免部署收费功能必须主动接入 Stack 授权验证；不要将 AppSecret 或发布凭证放在浏览器中。应用后续业务账号不由本协议管理。

## Compose 必须满足的要求

- 只交付预构建镜像；应用镜像通过声明的变量引用，CI 登记 `repository@sha256:...`，基础服务镜像也固定摘要。Dockerfile 基础镜像可以在开发时选择，但正式镜像应以摘要追踪。
- 只有 Stack 注入实例入口端口，应用不能固定宿主机端口、全局容器名称、宿主机目录或 Docker socket。
- 所有参数在 envFields / secretFields / domainSlots 中声明。密钥无默认值、不能写进镜像、源码、日志或工作流输出。
- 持久数据进入命名卷，进程可被重建。声明真实资源预算，不把临时容器运行成功当成业务负载容量测试。
- 有初始化或迁移时，显式声明 `lifecycle.infrastructure`（无基础服务填空数组）。数据库等基础服务必须有健康检查，平台先等其就绪，再用应用服务镜像运行迁移和初始化，最后启动业务服务。
- 实例生成的密码可声明为 `generatedSecrets: [{ key: DB_PASSWORD, encoding: hex, bytes: 32 }]`，对应 secretFields 必须是不可编辑的 preset 字段。平台只在首次绑定时生成并加密保存，重试复用；不要在每次启动时随机更换密码。
- 初始化和迁移使用 argv 数组，可安全重试，健康端点应表示可用状态；失败返回非零状态。步骤成功后写入进度，但崩溃边界仍可能重跑，应用必须保证幂等。数据迁移后仅回退镜像不等于数据回滚。
- 有持久数据必须提供备份、恢复及实际恢复验收。现有声明的 backup/restore 命令是结构要求，产物与通用执行协议尚未完成，不得据此宣称已能自动恢复。

## 交付验收清单

| 检查       | 验收证据                                           |
| ---------- | -------------------------------------------------- |
| 定义与版本 | 本地校验、固定源码提交、全部镜像摘要、平台登记结果 |
| 安装       | 空实例实际拉取、初始化、就绪、访问入口             |
| 隔离       | 同一服务器两个实例端口、网络、命名卷互不冲突       |
| 更新       | 老版本数据在新版迁移后可读取，失败处理经过测试     |
| 持久化     | 重建容器数据保留，备份在独立测试实例恢复成功       |
| 托管入口   | 默认子域名、HTTPS、访问检查及可追踪任务结果        |
| 免部署授权 | 未授权拒绝、购买后可用、过期或撤销后符合产品规则   |

当前生成工具只输出 `structuralValidation=passed`、`runtimeVerified=false`。内部安装内核已支持启动与续跑；客户部署入口、平台验收记录和发布门禁接通前，不可把模板、计划预览或单容器测试作为正式客户交付。
