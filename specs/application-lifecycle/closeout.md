# 接入与交付缺口收口

依据：2026-10-13 源码复核；起点 `631b184`。用户已授权按项实施与验证，沿用当前应用生命周期的需求和设计。

## 验收要求与顺序

1. **安装与发布完整性**：发放旧自部署安装命令时，必须固定安装脚本 SHA-256，下载成功且校验一致才执行；错误摘要、下载失败不得运行脚本。历史清单允许读取，缺少摘要的安装入口明确拒绝。启用商品及修改在售交付配置均不得绕过发布检查。
2. **通用交付闭环**：新 Compose 版本必须由平台受信执行链保存实际镜像拉取、初始化、健康、持久化及恢复证据；证据匹配不可变版本后才能发布。普通 CI 凭据不能提交可信运行证据。自部署和托管复用固定安装绑定，并完成 DNS/TLS 与自定义域名验收。
3. **免费领取**：免费应用具备自助领取入口、幂等权益发放与审计，不创建假支付；仅托管可独立收费。付费应用不能借此绕过支付。
4. **实际应用迁移**：Retail/Edu 在隔离实例完成完整新协议验收后再迁移，保留既有客户实例和明确回退条件。
5. **恢复接管与告警**：源隔离、目标资源预留、恢复验证、应用启动、域名切流和防双写有可执行流程；控制端重建单独演练。配置告警送达和独立外部探测，接收人未确认时不发送真实通知。
6. **迁移型升级**：明确迁移兼容条件、维护窗口、多镜像版本一致性、失败处置和数据保护；完成实际业务版本验收。随后进行容量测试和上线商品/真实资金验收。

## 实现约束

- 安装脚本摘要属于应用交付声明，不从客户端请求接受覆盖，不以下载后现算摘要当作可信预期值。
- 兼容读取旧记录不等于允许继续执行未经校验的安装脚本。
- 服务端发布门禁、客户入口和工程 CLI 使用相同规则；不能只靠后台按钮禁用。
- 失败部署保留资源，只有确认清理完成后释放；不可单凭任务失败就回收预算。
- 运行验收、代码测试、生产观察分别记录，不将模拟支付、缓存镜像或隔离数据恢复当作完整业务验收。
- 不新增应用内部员工/学生权限；不把组织席位和运行时 DRM 作为本轮前置条件。
