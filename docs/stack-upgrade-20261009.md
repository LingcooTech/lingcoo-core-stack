## 应用接入通用化

业务核心和节点执行器不再包含 Retail 应用代码、固定项目名前缀或固定 Node.js/PostgreSQL/Worker 服务假设。托管协议 v2 明确声明服务、资源权重、数据卷、初始化命令、镜像变量、入口服务与端口、域名变量和备份脚本。运行时配置转换由经过摘要校验的应用适配器承担。

- Retail/Edu 分别发布自己的适配描述，平台通过注册表识别能力。
- 节点未报告适配能力时不分配，未知协议或归属不匹配时拒绝执行。
- 既有 Retail 实例已补齐显式应用及 Compose 项目归属；实际容器与数据未重建。
- 两台节点均已更新。82 节点为只监控，118 节点支持 Retail/Edu。
- 异构 nginx 静态应用通过真实 Docker 安装、重复执行、备份和隔离恢复；无 API、Worker、数据库或 Node.js 业务运行时。
- 现有 Retail 的默认域名、自定义域名和五个服务正常；新协议下本地备份及异机备份成功。

这是“新增应用按协议提供适配产物，无需修改核心执行器”，并不表示任意第三方镜像无需适配即可完整交付。Compose、受信 Python 交付接口和备份产物约定仍是平台标准。客户自有服务器的公共交付 manifest 协议保持兼容，托管生命周期协议 v2 是独立层次。

## 微信支付

参照 Retail 的 Native V3 流程和 Edu 的签名校验方式，完成下单、查单、关单、通知、退款、退款查单的 V3 接入。后台提供七项配置：AppID、商户号、API v3 密钥、商户 API 私钥、商户证书序列号、微信支付公钥/平台证书、对应公钥 ID/证书序列号。

通知先对原始报文验签并核对密钥标识、时间窗口，再进行 AES-GCM 解密。业务事务校验订单、金额、币种，重复通知幂等处理。成功提交后返回 204，失败返回可重试的错误。保留 Stack 既有权益与托管计费逻辑。敏感配置加密存储，接口不回传原值。

旧 V2 API 密钥不会被当作 API v3 密钥。生产历史订单不删除、不修改。缺少 V3 配置时明确显示未配置，拒绝新支付。配置说明见 [微信支付升级](wechat-pay-v3-upgrade.md)。
