# 应用与 Stack 接入责任契约

日期：2026-10-03。状态：责任规划。Manifest v1 严格发布校验和 Retail 自部署样本已实现；完整 Release 服务、开发者 SDK 和云托管仍属后续阶段。当前实施证据见 [Retail 接入验收](retail-stack-onboarding-runbook.md)。

本文明确应用方、Stack、客户与基础设施供应商的职责，是 [业务闭环与托管方案](app-lifecycle-and-managed-hosting-plan.md) 的接入边界补充。现有自部署操作参考 [镜像交付标准](stack-app-delivery-onboarding-standard.md)；发生差异时，当前可执行能力仍以代码为准，新接入要求按阶段实施。

## 1. 分层原则

### 当前阶段范围

当前应用由 Lingcoo 自行开发、封装和维护，源码保存在各应用 Git 仓库。先完成标准接入、内部上架、销售、权益和镜像部署交付；保留客户应用列表与购买入口，暂不建设第三方开发者入驻、开放商城生态、佣金和分账体系。协议保持发布方无关，未来开放接入时不需要重写应用交付标准。

应用 CI 负责从固定源码版本构建并发布镜像；Stack 消费镜像及必要的声明元数据，不接收业务源码，也不在客户部署时克隆源码构建。一个应用可以提供 Web、API、Worker 等多个镜像，由同一个 Release 固定各组件的 digest。Manifest、版本说明和配置声明是交付元数据，不是额外要求交付源码。

当前镜像交付下，前后端分离可以通过独立 Web/API 镜像实现。Pages/OSS 等静态托管所需的静态制品作为后续可选交付扩展，不强制本期应用同时提供静态包，也不宣称容器镜像能直接部署到纯静态托管服务。

### 镜像更新流程

`源码修改 → CI 测试/构建 → 推送新镜像 → 登记新 Release → Stack 展示可更新版本 → 目标实例拉取新镜像 → 按声明执行迁移 → 重新部署 → 就绪验证 → 记录实际版本`

发布新镜像不自动覆盖所有客户。更新保留实例配置、密钥和持久数据；数据库迁移按应用声明的版本兼容规则执行。失败时保留旧版本服务或进入明确恢复流程，数据库不兼容时不能只回退镜像。源码仓与镜像仓由应用发布流程管理，Stack 保存版本引用和部署结果。

托管方案仍保留在规划中，云资源费用需记录归属；复杂按量转售、开发者分账和自动结算暂不建设。真实商业托管开放前确定简单、明确的收费和服务规则。

- 应用部署后的使用方式、账号、登录、成员和业务权限完全由应用自行处理，不属于 Stack 接入规划。
- Stack 负责商品、购买、授权、实例交付及其持续管理，提供统一协议和部署编排。
- 基础设施适配器负责将声明的资源需求映射到腾讯云、阿里云、国际云或自有服务器。
- 客户负责填写必要业务配置、选择服务方式、维护客户持有的账户和凭据；自部署时还负责自己的基础设施。

应用不导入 Stack 领域模块、不访问 Stack 数据库。Stack 不访问应用业务表执行日常业务逻辑。应用可采用不同语言和框架，满足交付协议即可；Starter 是推荐工程模板，不是平台准入绑定。

## 2. 责任矩阵

| 能力     | 应用方交付/负责                            | Stack 交付/负责                              | 客户或供应商边界           |
| -------- | ------------------------------------------ | -------------------------------------------- | -------------------------- |
| 业务功能 | 商品、课程、库存等业务流程及正确性         | 展示和售卖应用，不实现这些业务               | 客户运营自己的业务         |
| 软件商品 | 功能说明、feature code、支持范围、建议套餐 | 商品审核、Offer/Plan、价格与订单快照、上下架 | 运营确认正式价格与服务约定 |
| 软件交易 | 展示购买/升级入口或链接                    | 软件订单、付款验证、退款、软件权益           | 支付供应商执行资金处理     |

| 软件权益 | 声明交付范围 | 发放/续期/撤销购买、部署和更新权益 | 不介入部署后的业务权限 |

| 发布版本 | 构建制品、迁移、兼容范围、发布说明 | Release 登记/审核、制品校验、版本选择与发布记录 | 供应商提供制品托管 |
| 运行配置 | 配置 Schema、默认值、公开/密钥分类 | 收集、校验、生成基础配置、按实例安全注入 | 客户提供自己的商户等业务凭据 |
| 基础设施 | 声明 CPU/内存、数据库、存储、队列等需求 | 模板匹配、资源编排、归属、预算和回收 | 云供应商履行底层服务；自部署客户维护服务器 |
| 域名入口 | 支持配置公网地址、可信代理、回调及跨域规则 | 托管域名分配、DNS/TLS/路由编排与状态 | 自定义域名所有权与接入要求由相应主体提供 |
| 初始化 | 应用自己的安装初始化命令 | 按交付协议执行并记录结果 | 不对接应用账号体系 |
| 升级回滚 | 数据兼容策略、迁移顺序、回滚限制 | 编排备份、执行、健康验证、流量切换与记录 | 客户按套餐约定选择升级时间 |
| 备份恢复 | 声明所有状态来源、业务一致性及恢复校验 | 托管备份调度、加密/保留、恢复执行和演练 | 自部署客户负责备份执行，除非另购管理服务 |
| 可观测性 | 健康检查、结构化日志、必要指标及脱敏 | 收集运行状态、告警、部署进度及支持入口 | 不默认收集客户业务内容 |
| 退出迁出 | 业务数据/附件可导出，版本可识别 | 托管导出、迁移协调、资源删除及审计 | 按服务约定落实保留期和销毁要求 |

基础设施故障由 Stack 托管支持统一受理并协调供应商；应用缺陷由应用维护方修复。不能因为供应商负责底层服务，就让客户自行追踪所有供应商。

## 3. 应用接入必须提交的交付包

交付包是制品与元数据集合，源码可继续保存在应用方私有仓库。

1. **产品资料：** 稳定 appCode、维护联系人、描述/截图、功能代码、支持周期、所需第三方服务、数据类型和支持的交付模式。
2. **版本化 Manifest：** 协议版本、组件依赖、制品引用、资源需求、配置、生命周期命令和兼容性声明；不包含真实密钥。
3. **不可变制品：** Web/API/任务镜像 digest、revision 和构建来源；如需区域镜像，同步后验证制品一致性。静态包属于后续可选扩展。
4. **配置定义：** 字段类型/约束、用户输入与平台注入、公开与 secret、构建期与运行期、可变性及重启要求。
5. **生命周期能力：** migrate、bootstrap、health、ready；提供备份/恢复所需的一致性策略和应用校验，标准数据库备份可交由平台适配器完成。
6. **升级与数据说明：** 数据库引擎/版本/扩展、持久文件、队列状态、支持的升级源版本、迁移是否兼容旧应用、恢复步骤。
7. **交付权益：** 声明可交付版本和部署模式，由 Stack 校验购买、部署数量及更新权益；不要求应用接入运行时账号或业务权限系统。
8. **验收材料：** 从空环境安装、重复初始化、升级失败、备份恢复及关键业务冒烟测试；测试数据必须独立于生产数据。

静态网站、仅 API、小程序配套后端、包含常驻任务的应用需要不同能力集合。没有数据库的应用可声明无需迁移，不能为了统一清单提供假的迁移命令。自部署认证与各托管模板认证分别授予，不强制所有应用第一天支持所有部署目标。

## 4. Stack 提供的平台接入套件

以下为目标交付物，不能将现有内部 contracts/client 包描述为已经对外发布的完整开发者 SDK。

- **协议规范及版本策略：** JSON Schema/契约、错误码、状态机、兼容范围、弃用周期和升级指南。
- **验证工具：** Manifest 结构与语义检查、配置检查、制品校验、能力匹配、交付验收命令及可读报告。
- **接入样例：** 静态 Web + API + PostgreSQL 示例、仅 API 示例、自部署适配示例；样例不固化到某家云。
- **可选 SDK：** TypeScript 优先，封装部署配置交换、状态上报、重试和错误处理；标准协议允许其他语言直接实现。
- **发布接入：** 限定应用作用域的 CI 凭据、发布登记、审核结果及可部署区域状态；生产云主凭据不交给应用 CI。
- **平台控制台：** 商品审核、版本管理、模板兼容、配置收集、实例操作、运行状态和支持工单。
- **基础设施模板与适配器：** 云资源/域名/密钥/任务执行/备份；国内制品分发与网络检查包含在模板内。

当前由 Lingcoo 内部维护和审核自有或封装改造的应用，不规划第三方开发者入驻。发布操作仍需校验应用归属和操作权限。

## 5. 双方接口与信任边界

下列是协议能力名称，不是当前已经存在的 API 路径。

| 方向               | 能力                       | 身份与约束                                                    |
| ------------------ | -------------------------- | ------------------------------------------------------------- |
| 应用 CI → Stack    | 登记 Release、查询校验状态 | 发布凭据限定 appCode；不能创建其他应用版本或获取客户密钥      |
| 安装器 → Stack     | 兑换部署配置               | 短期凭据绑定 instanceId、Release、用途；保留安全重试语义      |
| 实例 → Stack       | 可选部署状态上报           | 实例专属运维凭据，与应用用户账号无关                          |
| Stack → 托管执行器 | 部署、升级、备份、恢复     | 任务绑定实例、操作 ID、参数版本和权限；命令来自已审核交付定义 |
| 自部署代理 → Stack | 拉取操作、回执结果         | 可选出站拉取，不要求客户开放任意远程管理端口                  |
| 浏览器 → Stack     | 购买、权益、实例管理       | 用户会话和资源所有权校验，不使用 App Secret 代替用户身份      |

Release 登记、支付通知、部署指令和状态上报均假设可能重复、延迟或乱序；使用幂等键、操作 ID、配置代次和实际观测时间，防止旧回执覆盖新状态。授权凭据要有签名/可信校验、有效期、作用域和密钥轮换机制，不能信任浏览器提交的 planId。

回调采用来源校验、防重放、超时和有限重试；不把应用任意 URL 或 shell 片段直接交给 Stack 主进程执行。应用生命周期命令在隔离任务环境中运行，只注入本次操作所需的实例资源权限。

## 6. 平台范围

Stack 管理上架、销售、购买权益、部署交付，以及用户选择的托管运维服务。部署后的应用使用和账号体系与 Stack 无关，不规划统一登录、用户映射、成员同步、业务角色或应用内交易集成。

应用不必为了上架而增加运行时 SDK 或每次业务请求的在线授权依赖。Stack 在购买、获取制品、创建部署、更新和托管服务操作时校验相应权益。应用自身已有的软件许可机制由应用维护，不在本次规划中统一改造。

托管数据库、存储、域名、备份和升级属于交付运维范围；应用业务表、用户账号及日常业务操作不由 Stack 管理。自部署可保留已有的状态上报和更新能力，这些能力不代表账号体系对接。

## 7. 托管与自部署的服务承诺

| 项目               | Lingcoo 托管                             | 客户自部署                                           |
| ------------------ | ---------------------------------------- | ---------------------------------------------------- |
| 资源/网络/域名维护 | Stack 按选定模板和服务约定负责           | 客户负责；Stack 提供校验和指导                       |
| 版本交付           | Stack 编排部署，可约定维护窗口           | 提供固定版本与安装/更新能力；客户执行或授权代理执行  |
| 状态真实性         | 云资源观测、任务结果与应用健康共同判断   | 上报是观测证据，离线表示未知，不能直接推断服务已停止 |
| 备份与恢复         | 按套餐落实调度、保留、恢复验证及 RPO/RTO | 应用提供兼容能力；客户负责执行，另购运维则另约定     |
| 费用               | 软件权益与托管费分别列示                 | 软件费用之外，基础设施通常由客户支付                 |
| 暂停与销毁         | 按通知/保留/导出/销毁流程执行            | 撤销平台权限不能代表已经远程删除客户数据             |

## 8. 接入与上架验收流程

1. 应用方登记身份与 App，提交产品资料、Manifest 和首个 Release。
2. Stack 自动检查协议、制品、配置和依赖；问题反馈给应用方修复。
3. 选择目标模板，检查地区、运行时、资源、域名、网络及费用条件。
4. 在隔离环境执行安装、初始化、交付冒烟、部署权益校验、升级和恢复。
5. 应用方确认业务可用；平台确认交付、隔离、权限和运维通过；运营确认价格、支持与数据保留条款。
6. 开放已验收的版本和部署选项销售。其他模板保持不可用，并说明未兼容或待认证。
7. 后续 Release 重新验证变更影响和兼容性；修改必需依赖、生命周期或数据结构不能仅靠版本号沿用认证。

首个试点需要证明：两个客户实例的数据/凭据互不访问；重复支付和部署不重复创建资源；迁移失败可恢复；部署及更新权益失效规则明确；国内目标不依赖不可达的安装或运行资源；客户可导出其数据。

## 9. 实施顺序与交付边界

1. 固化本文责任、协议字段与兼容规则，选一个真实应用制作交付包。
2. 建立严格 Manifest Schema、不可变 Release 和接入验证工具，保留现有自部署兼容。
3. 建立实例身份、模板能力匹配与最小接入 SDK；区分发布者、用户、安装器和实例凭据。
4. 对比腾讯云/阿里云模板，先跑通一个国内托管闭环及责任验收，再扩展其他模板。
5. 完善 Lingcoo 内部应用上架工具和客户部署管理界面，不扩展第三方开发者平台或应用账号集成。

Retail 首个样本已实现严格 Manifest 发布校验、固定镜像交付和隔离自部署闭环；其余接口、完整 Release 服务、SDK 发布和云托管仍须在对应阶段交付并验证。
